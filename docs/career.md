# 简历和面试使用指南

## 项目名称与角色

**ResearchLab｜研究型Agent运行与评测工作台（个人项目）**

角色可写“产品设计与原型实现”，前提是你能解释需求、取舍、实现与测试。代码由AI辅助完成时，面试如实说明，不写成独立从零手写所有代码。

## 简历条目（可按实际贡献使用）

- 面向产品经理的工具选型场景，设计研究型Agent工作台，定义候选版本、研究维度、证据来源及未知处理边界，打通Dify执行与本地Web面板。
- 设计检索、网页读取、事实抽取、限次补搜、报告和复核流程，沉淀来源/事实编号、失败与截断标记及独立人工意见，支持定位报告中的证据问题。
- 以软件选型、耳机和食品三个主题开展案例测试，识别引文与结论不匹配、历史价格时效和SKU信息缺失等问题；实现运行记录、版本对比、JSON导出与异常终态保存。

不要写“准确率提升XX%”“节省XX%研究时间”“服务XX用户”：目前没有这些证据。三个主题不是三个统计独立的大规模评测集；复跑次数不是用户数量。

## 60秒介绍

我做的是一个研究型Agent运行与评测工作台，首先服务产品经理的小规模选型研究。我发现只生成报告很难判断可信度，因此把重点放在任务范围、证据、失败记录和复核上。Dify负责执行流程，本地面板让用户查看每一步的输入输出、来源和问题。测试中系统曾把模型解释当成官方声明，复核把它拦下；食品案例则说明即使模型判定通过，证据仍可能不足。这让我把“复核通过”和“足够支持决策”看作不同状态。项目还是个人MVP，没有用户增长或准确率成果；下一步是固定评测集和人工标注。

## 常见追问

**为什么不用直接问ChatGPT？**

不是证明聊天工具不能研究，而是为重复任务保存明确输入、运行轨迹、证据与版本，方便复核和复测。是否真的节省时间仍需用户实验。

**为什么用Dify？你的贡献是什么？**

Dify提供编排与服务接口，降低原型成本。产品贡献是选择场景、定义输入/输出契约、证据结构、异常行为、评测和工作台交互；工程贡献是连接后端、持久化与界面。不要把Dify已有能力说成自己研发。

**模型检查通过为什么还会错？**

同模型检查有共享偏差；引文存在、字符串匹配、语义支持和研究充分性是不同层级。Venchi只有少量证据却模型PASS，是已观察到的不足，不能叫研究成功。

**怎么控制成本？**

限制候选、维度和补搜轮数；异常不自动反复执行；记录耗时与tokens。本版未接真实账单，也未实现平台级预算控制。

**算Agent还是工作流？**

研究计划和补搜含模型决策，但执行结构和轮数固定，更准确称研究型Agent工作流应用。不是开放式自主Agent平台。

**如果重做会先做什么？**

先做小型人工标注集，分别验证采集、事实条件、主张支持和需求充分性，再做界面扩展；避免每次遇错就往提示词追加某个产品的特例。

## 对应岗位的讲法

| 岗位方向 | 重点展示 | 不要夸大 |
|---|---|---|
| Agent/技术产品 | 输入输出契约、状态、事件、失败与重试取舍、工具边界 | 通用开发平台、生产SLA |
| 模型策略产品 | 错误分类、复核局限、待建人工标注与版本评测方案 | 模型训练、已证明的准确率提升 |
| 数据产品 | 来源/事实/主张关系、版本条件、指标口径与审计追溯 | 已建大规模高质量数据集 |

投递具体公司前按目标JD选择重点，不假设所有AI产品岗位都需要同一套能力。准备5分钟现场演示以及无法联网时的脱敏回放。
